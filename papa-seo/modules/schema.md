# Структурированные данные (JSON-LD)

Находит, проверяет и при необходимости генерирует разметку schema.org: что уже есть, что сломано, что даёт rich result в Google, что понимает Яндекс, что бесполезно. Сущности бренда и автора (sameAs, Wikidata) ведёт `eeat.md`, товары — `ecommerce.md`, локальный бизнес — `local.md`.

**Когда грузить:** режимы `page`, `audit`, `fix`; «проверь schema», «добавь разметку», «почему пропали звёзды», «нужна ли FAQPage».

**Входы:** URL или HTML; тип страницы (`references/page-types.md`); опционально — данные для генерации от пользователя (название, адрес, цены, автор). Отчёт «Расширенные результаты» из GSC — только чтение.

## Шаги

1. **Извлечь всё, что есть.** `python3 scripts/schema_check.py <URL|файл> --out schema.json` → типы с путём до узла, обязательные и рекомендуемые свойства по частым типам, синтаксис, `@id`-граф, статус типа в Google и в Яндексе, значения против видимого текста. Сырые блоки — в `page_facts.py` (`json_ld`, `microdata_types`, `rdfa_types`, `open_graph`); `schema_check.py --list-checks` печатает весь свой список параметров с источником. Если рендер доступен — сравнить с отрендеренной версией: разметка, вставленная JS-ом, обрабатывается с задержкой (facts-2026 §2).
2. **Гейт доказательств — обязательно до любых советов.** Перечислить найденные типы с путём (`@graph[2].@type = Product`). Совет «добавьте Organization/BreadcrumbList/Product» допустим, только если тип не найден ни в одном формате и ни в одной версии HTML. Это главная ловушка бенчмарков: предложить разметку, которая уже есть.
3. **Синтаксис.** Каждый блок парсится; есть `@context` и `@type`; URL абсолютные; даты в ISO 8601; числа без символов валют; enum — полные URL schema.org (`https://schema.org/InStock`); нет плейсхолдеров («[Company Name]», «TODO», «N/A»).
4. **Соответствие странице.** Каждое значение разметки видно на странице (цена, рейтинг, автор, даты, вопросы-ответы). Разметка невидимого — нарушение правил (facts-2026 §6). Рейтинг без видимых отзывов, `dateModified` свежее реальной правки, автор, которого нет на странице, — находки high. Даты и время: `page_facts` → блок `dates` (даты из JSON-LD рядом с найденными в тексте, флаги `event_utc_offset_on_ru_page`, `jsonld_time_not_in_text` — эвристика, проверить глазами).
5. **Статус типа в Google.** Сверить с facts-2026 §6: даёт ли тип rich result сейчас, выведен ли, ограничен ли. Выведенные типы не удалять принудительно (вреда нет), но и не рекомендовать ради выдачи. Self-serving reviews у LocalBusiness/Organization звёзд не дают.
6. **Обязательные и рекомендуемые свойства** — `schema_check.py` проверяет их по 22 частым типам (`markup.req_*`, состав — из registry.json и facts-2026 §6) и отделяет обязательные от рекомендуемых: рекомендуемых не хватает — это `low`, а не ошибка. Спорный или редкий тип — сверять по странице документации типа на developers.google.com (ссылки в facts-2026 §6).
7. **Связность графа.** Сущности сайта (Organization, WebSite, WebPage, Person, BreadcrumbList) — с устойчивыми `@id` вида `https://example.com/#organization`, `<URL>#webpage`; один и тот же объект на всех страницах описан одинаково и ссылается по `@id`, а не копией. Проверить: каждая ссылка `{"@id": …}` разрешается в сущность графа страницы или сайта; нет двух разных сущностей с одним `@id`; нет дублей Organization с разными названиями.
8. **Яндекс.** Яндекс понимает schema.org (JSON-LD, microdata), Open Graph и микроформаты, но не все типы; что именно поддерживается и что даёт эффект в выдаче — `references/yandex.md` §4. Не переносить выводы о rich results Google на Яндекс.
9. **Генерация (только по запросу).** Тип из таблицы ниже → JSON-LD только из значений, которые есть на странице или дал пользователь. Чего нет — поле не добавлять и написать в `unknowns`, не ставить заглушку. Результат — черновик блока + куда вставить, `approval_required: true`.
10. Проверка после правки: `page_facts.py` снова, плюс ручная проверка пользователем в Rich Results Test / валидаторе schema.org и в валидаторе Вебмастера (агент туда не ходит, если нет явного разрешения и доступа).

## Тип страницы → разметка

| Страница | Основная разметка | Замечание |
|---|---|---|
| Любая | WebSite (на главной), Organization, BreadcrumbList | Organization — один узел сайта с `@id` |
| Статья, новость, обзор | Article / NewsArticle / BlogPosting + author (Person с `@id`) | автор и даты — как на странице |
| Товар с покупкой | Product + Offer | merchant listing; детали — `ecommerce.md` |
| Обзор товара без покупки | Product + Review / AggregateRating | product snippet; отзывы видимые |
| Категория, листинг | ItemList (если есть карусель) или без особой разметки | не размечать как Product каждую карточку без нужды |
| Локальная точка | LocalBusiness (подтип) | одна точка — один узел; `local.md` |
| Вакансия | JobPosting | зарплата — только из текста вакансии |
| Событие | Event | даты, место/онлайн, статус |
| Вопрос с ответами пользователей | QAPage | не FAQPage |
| Форум, обсуждение | DiscussionForumPosting | |
| Профиль человека/автора | ProfilePage + Person | |
| Приложение, сервис | SoftwareApplication | цена/рейтинг — только реальные |
| Видео | VideoObject | |
| Страница FAQ от владельца | FAQPage допустима как словарь, rich result нет | не обещать выдачу (facts-2026 §6) |

## Проверки

| Что | Как проверить | Severity | Движок |
|---|---|---|---|
| JSON-LD не парсится | ошибка парсинга в `page_facts` | high | both |
| Нет `@context`/`@type` в блоке | структура блока | high | both |
| Значение разметки не видно на странице | сравнение значения и текста страницы | high | both |
| Рейтинг/отзывы в разметке без видимых отзывов; фейковые или нераскрытые стимулированные | разметка против текста | critical | google |
| Self-serving reviews в LocalBusiness/Organization ради звёзд | тип + источник отзывов | medium | google |
| Плейсхолдеры, пустые строки, «N/A» | значения полей | medium | both |
| Относительные URL, неверные даты, цена с символом валюты | формат значений | medium | both |
| Не хватает обязательного свойства для выбранного rich result | документация типа | medium | google |
| Рекомендуется или внедряется выведенный тип ради выдачи | facts-2026 §6 | medium | google |
| Разметка есть только после JS | сырой против отрендеренного | medium | google |
| Разные Organization на разных страницах (имя, лого, `@id`) | выборка URL | low | both |
| Висячие `@id`-ссылки, дубли `@id` | обход графа страницы | low | both |
| Microdata и JSON-LD описывают одно и то же с расхождениями | сравнение | low | both |
| Разметка противоречит canonical (url в разметке ≠ canonical) | `page_facts` | low | both |
| Тип, который Яндекс не поддерживает, подаётся как «для Яндекса» | references/yandex.md | low | yandex |

## Чего не делать

- Не предлагать разметку, которую не проверили на отсутствие.
- Не рекомендовать FAQPage и HowTo «для расширенного сниппета» или «для AI» (references/folklore.md).
- Не придумывать рейтинги, количество отзывов, цены, даты, адреса, sameAs-профили.
- Не размечать скрытый контент и не добавлять в разметку текст, которого нет на странице.
- Не обещать, что rich result появится: разметка не гарантирует показ.
- Не копировать описания типов из словаря schema.org в отчёт (лицензия, facts-2026 §6) — только имена типов и свойств.
- Не требовать удаления выведенных типов: вреда нет, есть только бесполезность.

## Выход

Находки по `templates/finding.schema.json`, `module: "schema"`, `evidence` — путь в JSON и фрагмент. Плюс инвентарь: тип → формат → где на странице → статус в Google (facts-2026 §6) → замечание для Яндекса. При генерации — черновик JSON-LD одним `@graph` с `@id`, список полей, которые не заполнены из-за отсутствия данных.
