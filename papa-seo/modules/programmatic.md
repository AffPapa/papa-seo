# Программатик: шаблонные страницы из данных

Решает, имеет ли право на индекс каждая страница, собранная из шаблона и таблицы (города × услуги, бренды × категории, сущности каталога, сравнения, глоссарий): есть ли у неё свои данные и своя польза. Опора — политика scaled content abuse (facts-2026 §9). Процент «уникальности текста» не используется (references/folklore.md).

**Когда грузить:** режимы `plan`, `audit`; «сгенерировать N страниц», «страницы под каждый город», «каталог из базы», «index bloat», «тонкие страницы».

**Входы:** источник данных (CSV/JSON/выгрузка БД) или его схема; шаблон страницы (HTML/Blade/Markdown); 5–10 примеров уже сгенерированных страниц (URL или файлы); план числа страниц. Опционально — выгрузка индексации GSC/Вебмастера по этим URL.

## Гейт «у страницы есть свои данные»

Страница проходит, только если **все** ответы «да»:

| Вопрос | Как проверить |
|---|---|
| Есть ли у записи данные, которых нет у соседних страниц шаблона (цифры, свойства, списки, даты, отзывы, контакты, цены) — и они видны в основном контенте? | Сравнить поля записи с соседними; посчитать непустые поля, специфичные для записи |
| Отвечает ли страница на реальный запрос, отличный от запроса соседней страницы? | Интент и спрос (`semantics.md`); без данных о спросе — `unknowns` |
| Можно ли объяснить пользователю, зачем эта страница отдельно, а не строкой в общем списке? | Одно предложение-обоснование на шаблон |
| Данные проверяемы: у каждой цифры есть источник, дата, способ подсчёта? | Поля `source`, `updated_at` в данных |
| Без подставленного имени город/бренд/сущность страница не превращается в копию соседней? | Убрать подстановку и сравнить две страницы |

Не прошла — варианты: объединить в агрегирующую страницу; оставить доступной, но `noindex` и без sitemap; не генерировать. Решение — по группе записей, не поштучно вручную.

## Шаги

1. **Инвентарь данных.** Число записей, доля пустых значений по полям, дубли и почти-дубли записей (совпадение большинства полей), поля-источники и даты обновления. Без источника цифр — находка high: на странице окажутся непроверяемые числа.
2. **Разложить шаблон** на статические блоки (одинаковы везде) и динамические (из записи). Оценить, где основной контент: если его образует статика с подстановкой названия — шаблон не проходит гейт.
3. **Прогнать гейт** по выборке 10–20 записей из разных квантилей заполненности (полные, средние, бедные). Вывести порог на правило по данным: «индексируем записи, у которых заполнены поля A, B и есть ≥ 1 отзыв» — без процентов текста.
4. **URL.** Один шаблон — одна схема URL; slug уникален и стабилен (не меняется при правке названия без 301); нет комбинаторного взрыва фильтров (`indexing.md`).
5. **Каноникализация и sitemap.** Прошедшие гейт — self-canonical и в sitemap; непрошедшие — не в sitemap; почти-дубли — canonical на основную или объединение.
6. **Перелинковка.** У каждой проиндексированной страницы есть входящие ссылки из хаба/категории и соседних сущностей (`links.md`, `python3 scripts/link_graph.py <edges.csv>`): сирот не публиковать.
7. **Метаданные.** Title/H1/description у страниц шаблона различаются по смыслу, а не только подставленным словом; при генерации AI — ручная проверка выборки (facts-2026 §9).
8. **Тексты, если генерируются моделью.** Каждое утверждение — из полей записи; чего нет в данных — не писать (SPEC правило 6). Скил `write.md`/`deai.md` для формулировок, `factcheck.md` для выборки.
9. **Выкладка партиями.** Не публиковать тысячи URL разом: партия → проверка индексации и качества → следующая. Публикация сверх согласованного объёма — только по явному «да» пользователя (policies/actions.md).
10. **Гейт доказательств для существующего программатика.** «Страницы тонкие» — только по выборке живых URL с полями записи, не по шаблону и не по числу слов.

## Проверки

| Что | Как проверить | Severity | Движок |
|---|---|---|---|
| Основной контент = статика + подстановка имени | сравнение двух страниц без подстановки | critical | both |
| Цифры на страницах без источника или даты | поля данных | high | both |
| Записи-дубли дают отдельные страницы | сравнение полей записей | high | both |
| Бедные записи (почти все поля пустые) в индексе и sitemap | заполненность × sitemap × meta robots | high | both |
| Страница отвечает на тот же запрос, что соседняя (каннибализация шаблона) | интенты, данные GSC при наличии | medium | both |
| Title/H1 отличаются только подставленным словом при одинаковом остальном | выборка мет | medium | both |
| Страницы-сироты: нет ссылок из хаба/категории | `link_graph.py` | high | both |
| Slug меняется вместе с названием без редиректа | история URL / код генерации | medium | both |
| Пустая страница (нет данных) отдаёт 200 вместо 404 или noindex | `http_safe.py`, `page_facts` | high | both |
| Комбинации параметров создают бесконечные URL | `indexing.md` | high | both |
| Тексты, сгенерированные AI, утверждают то, чего нет в данных | `factcheck.md` по выборке | high | both |
| Доля «Просканирована, не проиндексирована» по шаблону растёт | выгрузки GSC (`indexing.md`, шаг 5) | medium | google |
| Doorway-признаки: много страниц под варианты запроса ведут к одной цели | схема шаблонов и ссылок | critical | both |

## Чего не делать

- Не применять пороги «≥ 30–40 % уникального текста», «минимум N слов» (references/folklore.md).
- Не «уникализировать» страницы синонимайзером или перестановкой абзацев: это не добавляет данных.
- Не генерировать текст, которого нет в данных, ради объёма.
- Не публиковать весь массив за один раз и не отправлять тысячи URL в IndexNow одним днём без проверки партии.
- Не обещать трафик с N страниц.

## Выход

Находки по `templates/finding.schema.json`, `module: "programmatic"`. Плюс: правило индексации по данным (какие поля обязательны), таблица выборки записей с вердиктом гейта, схема URL, план партий выкладки с точками проверки. Все цифры о данных — из переданного источника; без источника — `null`.
