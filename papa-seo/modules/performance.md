# Скорость и Core Web Vitals

Говорит, есть ли у страницы проблема со скоростью у реальных пользователей, в какой метрике (LCP, INP, CLS) и в какой её части, и что чинить первым. Пороги и даты — facts-2026 §7. Код не правит: даёт причину, доказательство и черновик правки.

**Когда грузить:** режимы `page`, `audit`, `fix`; «медленный сайт», «красный CWV в Search Console», «LCP», «INP», «CLS», «PageSpeed ругается».

**Входы** (по убыванию веса): полевые данные — отчёт CWV из Search Console, CrUX (страница или origin), RUM пользователя; лабораторные — JSON Lighthouse/PSI, трасса DevTools; иначе — HTML и список ресурсов (`page_facts.py`). PSI/CrUX API — по ключу пользователя, бесплатно, отдельным шагом.

## Шаги

1. **Сначала поле, потом лаборатория.** Есть ли полевые данные по странице? Если нет — по origin, с явной пометкой «данные origin, не страницы». Нет поля вовсе (мало трафика) — так и написать; лаборатория тогда диагностика, а не оценка. Мобайл и десктоп — отдельно, p75 (facts-2026 §7).
2. **Выбрать метрику-виновника.** Только та, что в поле «нуждается в улучшении» или «плохо». Если все три зелёные — отчёт короткий: «проблем в поле нет», без списка микрооптимизаций.
3. **LCP — разложить на подчасти** (TTFB → задержка начала загрузки ресурса → длительность загрузки → задержка отрисовки; ориентиры долей — facts-2026 §7). Чинить самую большую часть, а не всё сразу.
4. **INP** — найти медленное взаимодействие (поле с атрибуцией или трасса): долгие задачи главного потока, тяжёлые обработчики, сторонние скрипты, большой DOM, синхронные перерасчёты стилей.
5. **CLS** — найти сдвинутый элемент и причину сдвига (картинка без размеров, вставленный сверху блок, баннер, шрифт, реклама без резерва). Жертва сдвига ≠ причина.
6. **Статика без рантайма.** Если есть только HTML: можно назвать вероятные причины (`page_facts`: LCP-картинка с lazy, картинки без width/height, блокирующие скрипты в head, нет `fetchpriority`, шрифты без `font-display`), но нельзя утверждать, что метрика плохая. Статус таких находок — `hypothesis`.
7. **Гейт доказательств.** «Добавьте preload/fetchpriority/width-height» — только после проверки, что этого нет. preload — только если трасса показывает позднее обнаружение ресурса.
8. **TTFB под нагрузкой.** Замер TTFB с сервера, который в этот момент нагружен (обход, деплой, крон), недействителен. Писать условия замера: откуда, когда, сколько повторов, кэш тёплый/холодный, CDN или origin.
9. **После правки** — повторить лабораторный замер в тех же условиях; поле обновится только с новыми визитами (CrUX — скользящее окно), улучшение в поле не заявлять сразу.
10. Яндекс: публичных порогов скорости, аналогичных CWV, пакет не знает; не приписывать Яндексу «пороги поведенческих» (references/folklore.md).

## Причины по метрикам

| Метрика / часть | Частые причины | Что проверить |
|---|---|---|
| LCP: TTFB | медленный бэкенд, нет кэша страницы, далеко от пользователя, цепочка редиректов | заголовки кэша, `chain` из `http_safe.py`, время ответа при низкой нагрузке |
| LCP: задержка загрузки | LCP-картинка обнаруживается поздно (CSS-фон, JS-вставка, lazy), нет приоритета | атрибуты LCP-элемента, его место в сыром HTML |
| LCP: длительность загрузки | тяжёлый файл, старый формат, нет `srcset`, нет сжатия | вес и формат, размеры против отображаемых |
| LCP: задержка отрисовки | блокирующие CSS/JS, веб-шрифт для LCP-текста, клиентский рендер | порядок ресурсов в head, `defer/async`, CSR |
| INP | долгие задачи, тяжёлые обработчики, сторонние скрипты (виджеты, аналитика), огромный DOM | трасса взаимодействия, список сторонних доменов |
| CLS | изображения/iframe без размеров, вставки над контентом, баннеры cookie, шрифты, реклама | атрибуты, места вставки, резерв места |

## Проверки

| Что | Как проверить | Severity | Движок |
|---|---|---|---|
| Метрика «плохо» в поле на мобайле для шаблона с трафиком | отчёт CWV / CrUX | high | google |
| Метрика «нуждается в улучшении» в поле | там же | medium | google |
| LCP-картинка на lazy-load | `page_facts`: первая крупная картинка | high | google |
| LCP-ресурс не в сыром HTML (CSS-фон, JS) | сырой HTML против рендера | medium | google |
| `fetchpriority="high"` на многих ресурсах | счётчик | low | google |
| Изображения/iframe без размеров на первом экране | атрибуты | medium | google |
| Блокирующие скрипты в `<head>` без defer/async | `page_facts` | medium | both |
| TTFB выше ориентира при низкой нагрузке, повторяемо | ≥ 3 замера с указанием условий | medium | both |
| Редирект перед основной страницей (http→https→www→слэш) | `http_safe.py` | medium | both |
| Нет сжатия текста (gzip/br) | заголовок `Content-Encoding` | low | both |
| Нет кэш-заголовков у статики | `Cache-Control` ресурсов | low | both |
| Сторонние скрипты на первом экране без необходимости | список доменов | low | google |
| Нет полевых данных вообще | CrUX пуст | info | google |

## Как писать отчёт

- Каждая цифра — с источником (поле/лаборатория), устройством, датой и условиями.
- «Плохой LCP на мобайле, p75 по CrUX за 28 дней, страница» — хорошо. «Скорость 43 из 100» — не метрика CWV, балл Lighthouse не равен оценке Google.
- Приоритет: метрика в поле хуже порога × трафик шаблона × простота правки. Без прогноза прироста позиций и трафика.

## Чего не делать

- Не упоминать FID, «CWV 2.0», VSI и прочее из references/folklore.md.
- Не выдавать балл Lighthouse за оценку Google и не сравнивать мобильные лабораторные цифры разных лет.
- Не утверждать «LCP плохой» без полевых данных или трассы.
- Не советовать preload «на всякий случай» и `fetchpriority` всем картинкам.
- Не прогонять Lighthouse/нагрузочные тесты по сотням URL продакшена: одна-три репрезентативные страницы на шаблон.
- Не обещать позиции за зелёные CWV (facts-2026 §7).

## Выход

Находки по `templates/finding.schema.json`, `module: "performance"`, `source_type`: `gsc` / `user_file` (CrUX, Lighthouse JSON) / `live_html`. Плюс таблица: шаблон → метрика → поле (p75, устройство, период) → подчасть-виновник → правка → как проверить. Лабораторные цифры подписаны условиями замера.
