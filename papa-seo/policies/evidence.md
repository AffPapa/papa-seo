# Политика доказательств

Цель — чтобы каждый вывод можно было проверить и чтобы отчёт не содержал ничего выдуманного.

## 1. Находка

Каждая находка — объект по `templates/finding.schema.json`:

| Поле | Что писать |
|---|---|
| `id` | короткий, стабильный: `idx-noindex-home` |
| `module` | модуль, который нашёл |
| `url_or_path` | где |
| `source_type` | `live_html` · `rendered` · `headers` · `robots` · `sitemap` · `gsc` · `webmaster` · `ga4` · `user_file` · `corpus` · `inference` |
| `fetched_at` | дата/время получения данных |
| `observation` | что увидено, одной фразой |
| `evidence` | фрагмент, заголовок, строка, число — то, по чему можно перепроверить |
| `status` | `confirmed` — видно в данных; `likely` — следует из данных с одним допущением; `hypothesis` — предположение, нужна проверка |
| `severity` | `critical` (страница/сайт выпадает из поиска) · `high` · `medium` · `low` · `info` |
| `engine` | `google` · `yandex` · `both` · `ai` |
| `fix` | конкретное действие |
| `approval_required` | правка меняет сайт или контент → `true` |
| `verify` | как проверить после правки |
| `unknowns` | чего не хватает для уверенности |

Источники не смешивать: сырой HTML, отрендеренный DOM, GSC, Вебмастер, GA4 и выгрузки пользователя — разные `source_type`. URL в sitemap не значит «в индексе». Балл рубрики не значит вероятность ранжирования.

## 2. Гейт «дефект действительно есть»

Перед советом «добавьте X» / «исправьте X»:
1. Проверь в данных, что X действительно нет или он действительно сломан (сырой HTML, заголовки, JSON-LD, robots). Самая частая ошибка агентов — предложить разметку, которая на странице уже есть.
2. Если проверить нельзя — статус `hypothesis` и в `unknowns` что нужно для проверки.
3. Если страница отдаёт ошибку, таймаут, пустой ответ, капчу — это находка о недоступности, а не «страница в порядке» и не «на странице нет X».

## 3. Полнота

- Утверждение «на сайте нет X» — только при полном покрытии. Иначе: «на 14 проверенных страницах из ~400 X нет».
- В каждом отчёте строка покрытия: сколько URL, какие источники, что пропущено и почему.

## 4. Числа

- Нет данных — `null` и слова «нет данных». Не 0, не «примерно», не оценка из головы.
- Частотность, позиции, клики, CTR, DR/DA, число ссылок, трафик — только из источника (GSC, Вебмастер, выгрузка, платный API по ключу пользователя) с указанием источника и периода.
- Никаких «+N % трафика», «рост за 30 дней», «вероятность цитирования N %».
- Пороги и даты правил — только из `references/facts-2026.md`; если там нет — проверить первоисточник и указать дату проверки.
- Средняя позиция GSC при сравнении периодов — взвешивать по показам или сравнивать по запросам, иначе вывод ложный.

## 5. Скоринг

Балл нужен не всегда. Если нужен:
- потолки при блокирующих условиях: `noindex` на целевой странице, 5xx, закрыт Googlebot/YandexBot, пустой контент → балл не выше 20/100 независимо от остального;
- каждая метрика помечена `DETERMINISTIC` (посчитано скриптом) или `HEURISTIC` (суждение);
- веса показаны рядом с баллом; `null` не считается нулём, а исключается из суммы с пометкой.

## 6. Тексты

Факты в статьях и на страницах — только из источника со ссылкой или из данных владельца. Нет подтверждения — `[NEED: что нужно]`, а не правдоподобная выдумка. Отзывы, цены, кейсы, статистику, личный опыт автора не сочинять.
